# Would a 65816 gdbstub for MAME be generally useful — and what would it take?

**Date:** 2026-06-11
**Prompted by:** the [Phase 2 plan](../plans/2026-06-11-drmon-mame-backend.md) rejecting
GDB RSP for the drmon↔MAME bridge ("MAME's gdbstub has no 65816 map"). Question raised in
review: *would implementing that map have value for other people, and what would it look
like?*

## Verdict (TL;DR)

Yes — moderate but real general value, at remarkably low cost. MAME has **two** gdb-stub
implementations (a C++ debugger module and a pure-Lua plugin), and adding 65816 support is
a ~35-line register map in either. The catch that keeps the value "moderate": **upstream
gdb itself cannot target the 65816** (no gdbarch — the binutils `w65` target was
assembler-only, never gdb-supported, and was removed in 2018; see the
[w65 investigation](2026-06-11-binutils-w65.md)), so out-of-the-box `gdb` is *not* a client — the real beneficiaries are
XML-aware RSP clients (IDA Pro, potentially Ghidra), custom tooling, CI harnesses, and the
Apple IIgs / Foenix-class communities for whom MAME is the only serious emulator with a
debugger. This does **not** change the Phase 2 decision (custom bridge), but an upstream
MAME PR is a cheap, decoupled community contribution worth queueing.

## What exists today

MAME ships two independent RSP servers:

1. **C++ debugger module** —
   [debuggdbstub.cpp](https://github.com/mamedev/mame/blob/mame0277/src/osd/modules/debugger/debuggdbstub.cpp)
   (`-debug -debugger gdbstub`, port via `-debugger_port`, documented at
   [docs.mamedev.org/plugins/gdbstub.html](https://docs.mamedev.org/plugins/gdbstub.html)).
   Full-featured: serves `target.xml` register descriptions (`qXfer:features:read`), maps
   `Z0` software breakpoints to native MAME breakpoints, proper `T05` stop replies.
   Supported registers maps at 0.277: i486, arm7, ppc601, r4600, m68k family, z80 family,
   m6502 family, m6809, score7, nios2, psxcpu. **No 65816/5A22.** Debugs the first/visible
   CPU only.
2. **Lua plugin** —
   [plugins/gdbstub/init.lua](https://github.com/mamedev/mame/blob/master/plugins/gdbstub/init.lua),
   291 lines, shipped in the Ubuntu package
   (`/usr/share/games/mame/plugins/gdbstub/init.lua`). i386 family **only**. Listens on
   `127.0.0.1:2159` via `emu.file("socket....")`, pumps from `emu.register_periodic`,
   detects stops by scraping `debugger.consolelog` for "Stopped at breakpoint N". Simpler
   and hackable without rebuilding MAME, but: no `target.xml`, assumes one uniform register
   width per CPU, `Z0` unimplemented (`Z1` hardware breakpoints carry the load), hardcoded
   `:maincpu` (master has [PR #10170](https://github.com/mamedev/mame/pull/10170) fixing
   that), byte-at-a-time memory reads.

Both share the limitation that only one CPU is debuggable — the SNES SPC700/PPU and SA‑1
are out of reach over RSP regardless.

## Who would actually benefit

| Audience | Benefit | Caveat |
|---|---|---|
| **Apple IIgs developers** | MAME is a primary IIgs emulator; there is *no* remote-debug story for it today. The IIgs CPU is the same `g65816` core. | Niche community; client tooling still needed. |
| **SNES homebrew / romhackers** | Scriptable, CI-able debugging (test harnesses attaching to a running game); MAME covers the arcade offshoots (Nintendo Super System, sfcbox, snesb bootlegs) that Mesen2/bsnes-plus don't. | For interactive debugging, [Mesen2](https://github.com/SourMesen/Mesen2) and bsnes-plus native GUIs are already excellent — RSP wouldn't displace them. |
| **Reverse engineers (IDA / Ghidra)** | IDA's gdb client + 65816 processor module against live MAME — exact precedent exists for m6502: [idapro_m6502](https://github.com/LucienMP/idapro_m6502) consumes MAME's gdbstub XML. | Ghidra's RSP path is less turnkey; unverified for 65816. |
| **Foenix / 65816 hobby-computer toolchains** | [Calypsi](https://www.calypsi.cc/) (C for 65816, Foenix C256/F256 targets) ships a source-level debugger that could grow a MAME backend. | Calypsi's debugger wire protocol is unverified — may not be RSP (open question). |
| **Tool authors generally** | A standard endpoint lowers the barrier for future DAP adapters, tracers, fuzzers. | Standard *server* ≠ ecosystem: every client today needs 65816 awareness added by hand, because **gdb upstream has no 65816 architecture** — the binutils [`w65` target](2026-06-11-binutils-w65.md) was assembler-only (never gdb), removed in 2018, and nothing replaced it. |

Adjacent prior art worth knowing: the romhacking community's
[SNI](https://github.com/alttpo/sni) / QUsb2Snes protocol does remote SNES *memory* access
(trackers, autosplitters) across emulators and flashcarts — but has no breakpoints, no
stepping, no register access. An RSP endpoint covers the *debugging* niche those
deliberately don't. Conversely, the fact that MAME's gdbstub went ~9 years without anyone
adding a 65816 map is honest signal that demand is niche — though each map that *is* there
(score7, nios2, psxcpu…) exists because one motivated person needed it once.

## What the implementation would look like

### Tier 1 — extend the shipped Lua plugin (works on stock apt MAME today)

Add a register map keyed by the CPU short-names (verified against
[g65816.cpp:105–107](https://github.com/mamedev/mame/blob/mame0277/src/devices/cpu/g65816/g65816.cpp):
`w65c816`, `w65c802`, `5a22`):

```lua
regmaps["5a22"] = {
    togdb   = { A = 1, X = 2, Y = 3, P = 4, E = 5, S = 6, D = 7, DB = 8, PB = 9, PC = 10 },
    fromgdb = { "A", "X", "Y", "P", "E", "S", "D", "DB", "PB", "PC" },
    regsize = 2,
    addrsize = 3,
    pcreg = "PC",     -- MAME's g65816 PC state is already the 24-bit linear value (%06X)
}
regmaps["w65c816"] = regmaps["5a22"]   -- Apple IIgs etc.
regmaps["w65c802"] = regmaps["5a22"]
```

The quick hack is ~15 lines and loadable against the installed MAME 0.277 via a
`-pluginspath` override — no rebuild. The *honest* version is ~1–2 days: the plugin
assumes one uniform register width (65816 mixes 16‑bit A/X/Y/S/D, 8‑bit P/DB/PB, 1‑bit E,
24‑bit PC), so it needs per-register widths, `qSupported`/`qXfer:features:read` serving a
hand-written `target.xml`, and `Z0` wired to `bpset` like `Z1`. Stop detection inherits
the consolelog-scraping fragility.

### Tier 2 — upstream C++ map in `debuggdbstub.cpp` (the proper contribution)

~35 lines using the verified state names
([g65816.cpp:964–975](https://github.com/mamedev/mame/blob/mame0277/src/devices/cpu/g65816/g65816.cpp)):

```cpp
static const gdb_register_map gdb_register_map_w65c816 =
{
    "w65c816",            // no official gdb arch name exists — ours to propose
    {
        {
            "mame.w65c816",   // no org.gnu.gdb.* standard feature for 65816 either
            {
                { "A",  "a",  false, TYPE_INT },
                { "X",  "x",  false, TYPE_INT },
                { "Y",  "y",  false, TYPE_INT },
                { "P",  "p",  false, TYPE_INT },
                { "E",  "e",  false, TYPE_INT },
                { "S",  "sp", true,  TYPE_DATA_POINTER },
                { "D",  "d",  false, TYPE_INT },
                { "DB", "db", false, TYPE_INT },
                { "PB", "pb", false, TYPE_INT },
                { "PC", "pc", true,  TYPE_CODE_POINTER },   // 24-bit
            }
        }
    }
};
// in gdb_register_maps:
{ "5a22",    gdb_register_map_w65c816 },   // SNES / NSS / sfcbox
{ "w65c816", gdb_register_map_w65c816 },   // Apple IIgs, Foenix-class
{ "w65c802", gdb_register_map_w65c816 },
```

The module already generates `target.xml`, maps `Z0`→native breakpoints, and emits proper
stop packets — the map is the *only* missing piece. Effort: the code is an hour; the cost
is building MAME from source for local verification and shepherding the PR (days–weeks of
calendar time, monthly release cadence; the apt package lags by years — which is exactly
why Phase 2 doesn't sit on this path). Bikeshed risk: the gdb arch/feature naming, since
no official 65816 name exists (precedent: MAME's `m6502` arch string is equally unofficial).

### Tier 3 — drmon as an RSP client (future option, not Phase 2)

If a 65816 map exists (either tier), `sliomame.cpp` could speak RSP instead of the custom
protocol: ~300 lines of client (framing, checksums, escaping, ack mode) plus an impedance
adapter — RSP *pushes* stop replies while drmon *polls* (`HandleSlaveInput`), manageable
with a non-blocking read. Payoff: drmon attaches to **any** RSP target (other emulators,
hardware probes) and sheds the bespoke Lua server. Cost: loses the protocol headroom for
drmon's SNES-specific opcodes (`SNES_READ_PPU`, OBJRAM/CRAM, SPC700) — RSP has no notion
of secondary address spaces or co-CPUs, and MAME's stubs only expose one CPU. In practice
that makes RSP a **dead end as the primary channel for console-specific development**: it
caps out at CPU-level debugging with PPU/VDP/co-processor state invisible, so it could
only ever be an *additional* backend beside the custom bridge, never a replacement.

## Relationship to Phase 2

Unchanged. The custom bridge remains right for drmon now: no upstream dependency in the
critical path, trivial client, and headroom for PPU/SPC700 ops RSP can't express. The
general-value play is **Tier 2 as a standalone upstream PR** (optionally proven first via
Tier 1 against the installed MAME in an afternoon) — decoupled from drmon entirely.

## Answers — implemented + verified (2026-06-13)

Both tiers were built and the register map proven live (MAME 0.277 + DKC). See
[the gdbstub-map plan](../plans/2026-06-13-mame-65816-gdbstub-map.md) (Tier 1 Lua, 14/14 verified;
Tier 2 C++ patch authored, build disk-gated), the
[IDA/Ghidra plan](../plans/2026-06-13-65816-rsp-clients-ida-ghidra.md), and concrete recipes in
`devsys/tools/mame-65816-gdbstub/clients.md`. Real answers to the original questions:

- **Does a 65816 processor module exist for IDA / does its GDB client work with the `target.xml`?**
  IDA ships no stock 65816 procmod (it has the 6502 family); 65816 disassembly comes from
  third-party modules. IDA's GDB plugin *does* consume a MAME-style `target.xml` (the idapro_m6502
  precedent) — and our description is **verified well-formed and self-describing**: `test_65816.py`
  confirms `qXfer:features:read:target.xml` returns the 10-register `w65c816` feature with the
  correct bitsizes/order and `g` decodes against it (24-bit PC intact). So the client-side gap is
  purely "load a 65816 disassembler," not "parse the registers." Final IDA-GUI attach is
  license-gated → documented recipe in `clients.md`.
- **Ghidra 65816 + RSP — connect without a custom agent?** ~~No.~~ **No, not turnkey.** Ghidra's
  "GDB" connector drives a local `gdb`, and gdb has **no 65816 gdbarch** — verified on stock gdb
  16.3: `set architecture w65c816|65816|65c816|m6502|6502|spc700` all return *Undefined item*
  (its only valid arches are i386 variants). A working Ghidra path needs a custom connector
  (TraceRMI / bespoke RSP agent) bridging our `target.xml` to Ghidra's own 65816 SLEIGH — plugin
  work, not configuration.
- **Mixed register widths in the `g` packet.** ~~Resolved by serving `target.xml`.~~ Both tiers
  serve a `target.xml` with explicit per-register bitsizes (`16 16 16 8 8 16 16 8 8 32`), so the
  byte layout is self-describing, not client convention. PC is pinned to 32 bits (24-bit value,
  zero-extended) for clean framing.
