# The binutils `w65` target — history, fit with the MAME ecosystem, and update/package/replace?

**Date:** 2026-06-11
**Prompted by:** the [65816 gdbstub investigation](2026-06-11-65816-gdbstub.md) noting that
"upstream gdb has no 65816 architecture" and citing the defunct binutils `w65` target.
Questions raised in review: what *was* w65, how could/did it fit the MAME ecosystem, and
does it need updating, packaging, or replacing — given this repo ships its own 65816 and
68000 assembler?

## TL;DR

`w65` was a 1995 Cygnus contribution giving GNU gas/ld a WDC 65816 **assembler-only** COFF
target — no gcc backend, no gdb support, no simulator, no debug-format story, ever. It sat
essentially untouched for two decades, was declared obsolete in binutils 2.28 (2017),
deleted during the 2.31 cycle (2018, commit "Remove w65 support"), and survives at HEAD
only as a tombstone ("support for it has been REMOVED"). **It needs neither updating nor
packaging** — there is nothing upstream left to package, and "updating" would really mean
writing a new ELF-based port plus a gdb architecture plus a compiler backend, i.e. the
smallest link of a three-link chain in which all three links are missing. **Its role here
is already filled natively**: the in-repo `spasm` assembler (65816 + 68000 + SPC700)
emits the symbol/debug data drmon parses, and the foundry apt pipeline we already operate
is the distribution channel when spasm gets ported. For the 68000 side, the upstream GNU
chain (m68k gcc/binutils/gdb) is alive — nothing to do at all.

## What w65 was

Contributed in 1995, "Hacked by Steve Chamberlain of Cygnus Support"
([cpu-w65.c](https://android.googlesource.com/toolchain/binutils/+/refs/heads/donut/binutils-2.17/bfd/cpu-w65.c)) —
the same engineer behind the h8/300, SH, and z8k ports of the Cygnus contract-work era.
The target accepted both `w65` and `w65816` names and comprised:

| Piece | What it gave you |
|---|---|
| `bfd/cpu-w65.c` | architecture: 16-bit word, 24-bit address space |
| `bfd/coff-w65.c` | **COFF** object format (never ELF) |
| `gas/config/tc-w65.c` | the 65816 assembler |
| `opcodes/w65-dis.c` | objdump disassembly |
| `ld` emulation | linking COFF objects |

What never existed upstream, at any point: a **gcc backend** (no C compiler ever drove
this assembler), a **gdb architecture** (`gdb/configure.tgt` has never listed w65), a
**simulator** (no `sim/w65`), or integration with any debug-info consumer. It was an
island: you could assemble and link 65816 COFF, then `objcopy` to a binary — and that was
the whole workflow. Who Cygnus' paying customer was is not publicly documented; no visible
user community ever formed around it.

### Timeline (verified against the [binutils-gdb repo](https://sourceware.org/git/?p=binutils-gdb.git;a=summary))

| When | State |
|---|---|
| 1995 | Contributed (copyright years on the files: 1995–2002 touch-ups only) |
| through 2.27 (2016) | Live target (`w65-*-*` configurable), but effectively unmaintained bit-rot |
| 2.28 (2017) | Moved to the obsolete list (build refused without `--enable-obsolete`) |
| 2.31 cycle (2018) | Files deleted — commit "Remove w65 support" ([file history](https://sourceware.org/git/?p=binutils-gdb.git;a=history;f=bfd/cpu-w65.c)) |
| HEAD today | Tombstone only: `w65-*-*` in [config.bfd](https://sourceware.org/git/?p=binutils-gdb.git;a=blob;f=bfd/config.bfd;hb=HEAD)'s "configuration is now obsolete and support has been REMOVED" block |

(Correction to the gdbstub investigation's off-hand "removed two decades ago": the *files*
lasted until 2018 — but the target was dead weight for most of its life.)

## How it did / could fit the MAME ecosystem

**Did: never.** MAME consumes ROM images; w65 could in principle produce one via
`objcopy`, but it had no console-specific linkage (SNES LoROM/HiROM layout, checksums,
headers), no debug-info path into any debugger, and no debugger could attach to 65816
anyway — gdb couldn't speak the architecture and MAME's gdbstub (which postdates w65's
obsolescence) never gained a 65816 map.

**Could: only as one link of a chain that's missing all three.** The instructive contrast
is the 68000 — newly relevant since Phase 2 now covers genmon. For Genesis work, a
complete GNU pipeline exists **today**: `m68k-elf` gcc + binutils, gdb's mature m68k
gdbarch, and MAME's `m68000` gdbstub register map. Every link alive and maintained. For
the 65816, all three links are missing: no compiler backend (gcc or llvm), no gdbarch, no
MAME gdbstub map. A revived w65 would restore only the smallest link (assembler/linker) —
the one the retro community has already rebuilt several times over (see below). Modern
groundwork for doing it *properly* exists as discussion — a
[psABI for w65 thread on 6502.org](http://forum.6502.org/viewtopic.php?f=2&t=6791)
sketching a new **ELF** ABI — but it treats the old COFF target as historical reference,
not a starting point.

## Update, package, or replace?

**Update? No.** The code is deleted, COFF-based, and pre-ISO-C era; binutils policy for
reinstatement would demand an ELF port with an active maintainer. That's a
write-from-scratch project justified only if a 65816 compiler backend and gdb support were
coming to meet it — neither is on any horizon we depend on. drdevtools has no need it
would serve.

**Package? Nothing left to package.** You can't ship what upstream deleted; packaging
binutils ≤ 2.27 with `--enable-obsolete` would distribute 2016-era tools emitting COFF
that nothing downstream consumes. And yes — the packaging *pipeline* question is already
answered in this project: the foundry apt repo and the `/package` workflow exist, and
TODO already plans a drmon `.deb`. The right payloads for that channel are the native
tools, not a resurrected w65.

**Replace? Already replaced, twice over.**

1. **In-repo, for the DR-native workflow:** `tools/spasm` is a multi-target macro
   assembler with 65816, 68000, *and* SPC700 code generators (`cam816.asm`, `cam68.asm`,
   `cam700.asm`) — and unlike w65, it pairs with a real debug story: it produces the
   symbol/debug data drmon's loaders (`sld.cpp`, `symbol.cpp`) natively parse, and built
   the in-tree monitors (`snesmon.prc`, `genmon.prc`). Caveat for planning: spasm is a
   DOS program whose assembler core is written in x86 assembly — porting it to Linux is
   its own drmon-Phase-1-shaped project, not a quick win. When that happens, the foundry
   apt repo is its distribution channel.
2. **Community, for everyone else:** the 65816 assembler niche w65 vacated has long been
   filled by maintained tools — [ca65](https://cc65.github.io/), [WLA-DX](https://github.com/vhelin/wla-dx),
   [64tass](https://sourceforge.net/projects/tass64/), [asar](https://github.com/RPGHacker/asar) —
   plus C via [PVSnesLib](https://github.com/alekmaul/pvsneslib)'s tcc-derived 816
   compiler and the commercial [Calypsi](https://www.calypsi.cc/) toolchain. None of them
   needed w65.

## Verdict

w65 is a historical curiosity, not a gap. Do nothing on it. The actionable items in this
territory remain: (1) the MAME gdbstub 65816 register map as a standalone upstream
contribution (per the [companion investigation](2026-06-11-65816-gdbstub.md)) — for the
68000/Genesis side that map already exists upstream; and (2) eventually port + package
`spasm` through the foundry apt pipeline as the native assembler that actually integrates
with drmon (candidate TODO item, not yet filed).

## Open questions

- Sizing the spasm port (x86-asm assembler core: rewrite vs. translate; the `.cpp`
  front-end portions look Phase-1-portable).
- Whether the [6502.org psABI effort](http://forum.6502.org/viewtopic.php?f=2&t=6791) or an
  llvm 65816 backend matures into a chain worth tracking (would revive the gdbarch +
  gdbstub-map questions with a real constituency behind them).
- Cygnus' original w65 customer (curiosity only; would explain the target's shape).
